## Context

项目当前为空目录，尚无前端框架、素材或测试基础。目标是浏览器本地运行的星穹幻想抽卡演示。画面、卡面和动画由 HTML Canvas 2D 绘制；角色使用原创插画。用户已确认单抽、十连、基础概率、十连 4★ 保底、逐张揭晓、跳过及桌面/手机适配。

## Goals / Non-Goals

**Goals:**

- 建立结构简单、可本地运行和验证的前端页面。
- 让抽取规则与视觉表现分离，保证随机结果可测试，动画始终展示同一份结果。
- 在桌面与手机上保持画面清晰、交互区域可用，并以原创角色插画支撑卡面品质。

**Non-Goals:**

- 账号、货币、付费、后端 API、真实卡池配置与跨会话保底。
- 角色养成、背包、历史记录或概率公告后台。

## Decisions

### 1. 采用轻量 TypeScript 前端与 Canvas 2D 渲染

以后续实现阶段的 Vite + TypeScript 单页应用作为构建基础。Canvas 2D 负责主画面、卡牌、粒子与转场；少量 HTML 负责挂载画布及必要的语义、辅助操作。相较引入 WebGL 或大型游戏引擎，此方案更适合当前二维卡面与粒子动画，启动和维护成本也较低。所有交互坐标须由 CSS 显示尺寸映射到 Canvas 逻辑坐标；画布按设备像素比缩放并设置合理上限，避免高分辨率手机过度消耗显存。

### 2. 抽卡规则是无 UI 依赖的纯逻辑

角色池按稀有度组织；一次基础抽取先决定 3★/4★/5★，再在对应池中选角色。随机数入口可注入，方便用确定性序列验证阈值和保底。十连先独立进行十次基础抽取；仅当十次均为 3★ 时，将最后一张提升为 4★ 并重新选取对应角色。这样每次十连恰好十张，且基础概率的含义明确。此保底只作用于当前十连，不建立跨次计数。

### 3. 抽取结果先确定，动画只负责呈现

用户触发后立即生成并冻结本次结果，随后进入 `idle → flight → reveal → summary/result → idle` 的展示流程。`flight` 时播放约 2 秒星轨；`reveal` 按顺序逐张显示；十连完成后进入 `summary`，单抽进入 `result`。跳过操作直接转换到对应最终展示状态，读取同一份冻结结果。非空闲状态忽略新的抽卡输入，避免重复抽取。相较在揭晓时逐次随机，这种方式能确保正常播放与跳过得到相同结果。

### 4. 视觉素材与交互策略

为每个稀有度准备可识别的原创角色插画，配套角色名称、星级、卡框和分层粒子效果。优先将插画打包为本地静态资源，避免运行时外部网络依赖。Canvas 绘制星空与星轨，5★ 使用更强的光效和节奏，但星级与角色名称始终可读。桌面提供鼠标交互，手机提供触控交互；跳过入口在动画期间可见。

## Risks / Trade-offs

- [Canvas 文本和交互的可访问性较弱] → 为关键按钮提供语义化 HTML 对应入口，并保证结果有可读取的文本描述；不让视觉特效成为唯一的稀有度提示。
- [高分辨率画布和粒子数量影响移动端帧率] → 限制设备像素比与粒子数量，根据帧时间减少特效密度。
- [原创插画尺寸与构图不一致] → 在素材制作时统一人物安全区和卡面裁切比例，并在桌面与手机尺寸下人工检查。
- [概率测试依赖随机性难以稳定重现] → 抽卡函数接受可注入随机源，以边界值和固定序列进行确定性验证。

## Migration Plan

空项目无需迁移。后续实现按竖切任务逐步建立可运行页面；回退时移除本变更新增的前端文件和素材即可。

## Open Questions

无影响本阶段任务拆分的待决问题。具体角色名称和插画构图可在素材制作时确定，但须满足规格中的原创与稀有度可辨识要求。
